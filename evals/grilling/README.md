# Grilling：需求澄清应当问到什么程度？

这组探索性实验研究 AI 在需求澄清中何时应当继续提问、何时应当自己判断、何时应当请用户确认并交付文档。案例来自 [casey/just](https://github.com/casey/just) 已解决的功能 issue，以合并前的代码、issue 讨论和对应 PR 构造需求与核对项。

**主要发现：** 只催促收尾会漏掉重要决策；增加完整性检查又可能引发反复确认。v3 修订版（`v3b`）把“不同答案是否影响结果”进一步收紧为“是否缺少只有用户才能提供的目标、偏好或约束”，并记住用户授权自行决定的范围。在目前的小样本中，它表现出沟通完整性与便捷性之间更好的平衡；证据不足以证明它对所有项目或模型都最优。

## 阅读入口

下载并用浏览器打开 **[index.html](index.html)**。这是唯一的页面入口，不需要服务器或构建：

- **报告与图表**：研究问题、方法、各版本效果与取舍、局限，以及可切换批次和案例的柱状图。
- **对话记录**：选择模型批次、issue 和版本，逐条对照助手与模拟用户的完整回复，并查看产出的文档。

GitHub 文件预览不会执行 HTML；需要先下载。也可以在本目录运行 `python3 -m http.server 8000`，访问 `http://localhost:8000`。

## 批次与统计口径

| 数据批次 | Agent / 模拟用户 | 数量 | 用途 |
| --- | --- | ---: | --- |
| `claude` | Opus / Sonnet | 12 | 3 个案例，baseline 与 v1 各重复两次 |
| `sol` | GPT-6-sol / GPT-6-luna | 40 | 12 个案例的 baseline、v3、v4，加 4 次重复 |
| `small` | GPT-6-sol / GPT-6-luna | 2 | 单案例比较 v3 与 v3b；v3 运行由用户中断 |
| `grok` | Grok 4.7 / Grok 4.6 | 6 | #1748 的 baseline、v1、v2、v3、v4、v3b 各一次 |
| `diag1`、`diag2` | 见记录的模型字段 | 13 | 调试期间的对话，排除在正式统计之外 |
| `probe` | 固定历史问题 / Luna 与 Grok 4.7 回复 | 8 | 4 组配对回复重放，不是 8 次完整对话 |

共 **81 条展示记录**：73 条对话记录和 8 条回复重放记录。正式对话共 60 次，其中 58 次完成文档、1 次达到轮数上限、1 次被中断。不同批次的案例与模型不同，不能将所有结果混为一个版本排行榜。早期“问题数”和后期“助手轮数”也不是同一个指标。

## 各版本改变了什么

| 版本 | 方法 | 主要取舍 |
| --- | --- | --- |
| baseline | 加载相同 skill，不注入 grilling-check | 提供追问与收尾行为的参照 |
| v1 | 下一问须改变文档中的具体句子；列出假设后直接交付 | 收尾快，但用户没有独立否决假设的机会 |
| v2 | 收尾清单后停下，等用户确认 | 恢复纠错机会，但可能把大量决策塞进确认清单 |
| v3 | 关注用户可见行为与重大约束；一问一答；确认后交付 | 更好地保留重要分歧，但“答案会改变结果”仍可能触发非必要追问 |
| v4 | 加强合同完整性与依据检查，允许发现分歧后重新提问 | 可能找出遗漏，也增加检查和反复确认成本 |
| v3b | 在 v3 上检查是否缺少用户专属信息，并记住授权范围 | 减少可自行判断的提问；仍依赖代理判断和模拟用户纠错能力 |

这些文件保留实际运行的措辞，包括后来讨论过但尚未替换的具体检查清单。后续建议没有被倒写进历史提示词。

## 实验边界

- 这是逐步探索的实验，不是预注册、充分重复的对照研究。v3b 的完整 Grok 对比仅覆盖一个案例，每版一次。
- Sol 与 Grok 由驱动每轮注入提示词，不能据此声称已验证 HNM 的原生 hook 集成。初期 Claude 使用原生 UserPromptSubmit hook。
- 模拟用户会遗漏、编造或改变偏好。#1748 隐藏 brief 对空列表的描述存在歧义；报告保留了对应错误与局限。
- Sol 正式批次的 39 份评分来自模型，1 份由主助手补评；部分结果经主助手复核。这不等于独立人工标注。
- 没有“只在开头加入同一提示词”的对照组，也没有对 v3b 两项修改分别做消融。不能单独归因于提醒的位置、频率或其中某一条规则。

## 复现

浏览、下载和核对归档完全离线，不需要模型账号：

```sh
python3 scripts/verify.py
```

重跑 Grok 需要当时兼容的 `grok` CLI、模型权限及完整 just Git 历史。驱动请求 `grok-4.7` 作为 agent、`grok-4.6` 作为模拟用户；原运行返回的模型用量标签带有 `-build` 后缀。CLI 与服务端模型变化可能影响重跑结果。

```sh
git clone https://github.com/casey/just.git /tmp/just-grilling-source
python3 scripts/grok/run.py \
  --just-source /tmp/just-grilling-source \
  --output /tmp/grilling-rerun \
  --case 1748 --workers 6
```

默认运行全部六组，包括 baseline；可用 `--arms base v3b` 选择部分组。输出目录必须不存在。每组最多 30 个助手轮次；出现 PRD、ADR 和 spec 文件即结束。驱动保留原实验的自动批准工具调用设置，应在可丢弃的独立环境中运行。重跑会产生模型调用费用及原始日志，输出不会自动更新本归档。

Grok 入口仅调整了路径配置、参数和独立模拟用户协议的读取方式，并将 baseline 纳入默认组；提示词、模型、轮数上限和停止条件保留原实验逻辑。归档整理时只检查脚本语法与参数入口，没有再次调用模型。

其他三个目录中的驱动作为历史方法材料保留，依赖原来的临时目录布局和 CLI 参数，不能直接在归档目录执行。复用前须按代码恢复案例、skill、hook 文件布局、just checkout 和对应 CLI；Claude 驱动还依赖已构建的 hnm。`method/manifest-final.json` 的摘要和检查记录描述原 Sol 运行产物，不是此归档文件的校验和。
